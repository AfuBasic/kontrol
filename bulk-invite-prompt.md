# BULK VISITOR INVITE — ENGINEERING PROMPT

## 1. CONTEXT

You are working on Kontrol, a Laravel 12 + Inertia React estate management application. This feature lives inside the Organization Admin area — specifically the Access / Visitors section.

There is already a working single-visitor invite flow (see screenshots: "Invite visitor" bottom sheet). This feature adds a bulk invite that accepts multiple emails, generates individual access passes for each recipient, and delivers them via email in the background.

The bulk invite is triggered from the visitors page. It should feel like a natural extension of the existing invite flow, not a separate system.

---

## 2. OBJECTIVE

Build a bulk visitor invite feature that:

- Accepts up to 30 email addresses at once
- Creates one access pass per recipient
- Sends each invite as a branded PDF attachment via email
- Processes everything in the background using queued jobs
- Handles partial failures gracefully (e.g., 28 of 30 succeed)
- Validates all inputs before any invites are created

## 7. BACKEND ARCHITECTURE

### Queue architecture (critical)

Do NOT generate and send emails synchronously in the HTTP request. Every email must be dispatched to a queue.

Job design:

BulkInviteJob
  - handles the entire bulk operation
  - receives: organization_id, estate_id, invited_by_user_id, expiry_date, role, purpose, array of emails
  - processes each email as an independent sub-job
  - each sub-job: create access code → generate PDF → send email
  - individual sub-job failures do not fail the entire batch
  - stores per-recipient status (pending → processing → sent / failed)

GenerateInvitePdfJob
  - receives: access_code_id
  - generates the PDF
  - stores it temporarily (S3 or local storage, 24h TTL)
  - passes the PDF path to the email job

SendInviteEmailJob
  - receives: access_code_id, recipient_email
  - attaches the PDF
  - sends the email
  - updates the invite status to 'sent' or 'failed'

Why three jobs:

BulkInviteJob is the orchestrator. It batches the work and tracks overall progress. GenerateInvitePdfJob is CPU-intensive (PDF generation, QR code rendering) and should be on its own queue. SendInviteEmailJob is I/O-heavy (SMTP/API call) and should be on its IO queue. This separation means PDF generation and email sending can run concurrently for different recipients.

Job priority:
- Bulk invite jobs should use high priority — these are user-initiated and should complete quickly
- PDF generation can be medium — slight delay is acceptable
- Email sending can be low — but should start immediately after PDF is ready

### Database design

No new table needed for the core invite. The existing access_codes table already stores individual access codes. Add a bulk_invite_batches table for tracking:

Schema::create('bulk_invite_batches', function (Blueprint $table) {
    $table->id();
    $table->foreignId('estate_id')->constrained();
    $table->foreignId('organization_id')->nullable()->constrained();
    $table->foreignId('invited_by_user_id')->constrained('users');
    $table->string('status'); // processing, completed, partially_failed, failed
    $table->integer('total_recipients');
    $table->integer('successful_sends')->default(0);
    $table->integer('failed_sends')->default(0);
    $table->date('expiry_date');
    $table->string('role')->nullable();
    $table->string('purpose')->nullable();
    $table->json('errors')->nullable(); // array of {email, error_message}
    $table->timestamp('completed_at')->nullable();
    $table->timestamps();
});

Each access code generated by the batch gets a bulk_invite_batch_id foreign key on the access_codes table.

### Validation

Before any database writes:
1. Validate email count: 1–30, reject above 30 before touching the database
2. Validate email format: all emails must be valid RFC format
3. Check duplicates: within the batch, no duplicate emails
4. Check existing: no recipient should already have an active, unexpired access code for the same organization (warn, don't block — the user may want to re-invite)
5. Validate expiry date: must be between today and 30 days from today

Validation runs in the HTTP request. If validation fails, nothing is queued. If validation passes, the batch record is created and jobs are dispatched.

### Idempotency

If the user double-clicks "Send invites" or refreshes the page mid-processing:
- The batch ID is returned in the HTTP response
- A client-side token prevents double submission
- If the same batch is retried, only failed recipients are re-queued
- Access codes are not duplicated — each email maps to one code per batch

### Failure handling

Per-recipient failures (most common):
- Invalid email (caught at validation, not queued)
- Email service timeout → retry 3 times with exponential backoff (30s, 2min, 10min)
- After 3 failures → mark as failed, store error message, continue with next recipient
- User sees: "2 invites failed to send. Retry?" with specific error reasons

System-level failures (rare):
- Queue connection lost → batch status = failed, all recipients marked failed
- User sees: "Something went wrong. Please try again."
- No partial data loss — batch record and access codes are created in a database transaction before jobs are dispatched

### Transaction safety

DB::transaction(function () use ($data) {
    $batch = BulkInviteBatch::create($data);
    foreach ($emails as $email) {
        AccessCode::create([
            'code' => generateCode(),
            'bulk_invite_batch_id' => $batch->id,
            // ... other fields
        ]);
    }
    // Jobs dispatched AFTER transaction commits
});
// Jobs dispatched here, outside transaction
BulkInviteJob::dispatch($batch);

This ensures: if the transaction fails, no orphaned access codes exist. Jobs only fire after the database state is consistent.

## 8. PERFORMANCE CONSIDERATIONS

30 recipients = 30 PDFs + 30 emails.
- PDF generation: ~200ms each = ~6 seconds total CPU time
- Email sending: ~3-4 seconds each = ~90-120 seconds total wall time
- Total wall time with concurrency (3 parallel): ~30-40 seconds

With queued jobs:
- HTTP request completes in ~500ms (batch record created, jobs dispatched)
- User sees immediate confirmation
- Emails arrive individually over the next 30-60 seconds
- No timeout risk

Queue concurrency:
- Set BulkInviteJob to process 5 recipients at a time per worker
- PDF generation and email sending for each recipient are sequential within the sub-job (PDF must exist before email attaches it)
- But different recipients' jobs run in parallel

Rate limiting:
- If using an external email API (e.g., Resend, Postmark), respect their rate limits
- Throttle to match the email provider's limit (e.g., 100 emails/minute)
- With 30 recipients max per batch, this is never a problem at the batch level
- But if multiple orgs send bulk invites simultaneously, the queue worker should throttle globally

## 12. WHAT NOT TO DO

- Do NOT generate or send emails synchronously in the HTTP controller
- Do NOT create access codes outside of a database transaction
- Do NOT allow more than 30 recipients per batch
- Do NOT generate QR codes synchronously in the HTTP request
- Do NOT block the UI while emails are being sent
- Do NOT create a separate invite system — reuse the existing AccessCode model and generation logic
- Do NOT change the single-visitor invite flow
- Do NOT store PDFs permanently — they should expire after 24 hours
- Do NOT expose internal error details to the end user — generic "invite failed" is fine for the recipient, details go to logs

## 13. ENGINEERING EFFICIENCY SUMMARY

The key efficiency decisions:

Job separation: PDF generation (CPU) and email sending (IO) are separate jobs. They can run in parallel across recipients. A batch of 30 doesn't block on 30 sequential PDF generations.

Transaction boundary: Database writes happen in a transaction. Jobs are dispatched after commit. No orphaned records if something fails mid-write.

Per-recipient failure isolation: Each recipient is an independent sub-job. One bounced email doesn't fail the batch. The user sees granular status.

Idempotent retry: Failed invites are retried individually. No duplicate codes. No duplicate emails.

Client-side validation first: Email format, duplicates, and count are validated in the browser before the request hits the server. Invalid batches never reach the queue.

PDF as a job: QR code generation and PDF assembly are CPU work. Offloaded to a queue so the HTTP request stays fast and the work scales across workers.

Max batch size: 30 is the hard limit. This keeps processing time bounded (~40 seconds for a full batch) and prevents abuse.
